# Авторский голос

Локальный конструктор авторского голоса. Отдельные тексты анализируются через OpenRouter; выбранные приемы объединяются в подробную инструкцию и компактную промпт-версию. Обе инструкции можно править и экспортировать независимо от проверки.

## Запуск в Windows

1. Запустите Docker Desktop.
2. Откройте PowerShell в `C:\ai_voicers` и выполните `docker compose up -d --build`.
3. Откройте [http://127.0.0.1:3333](http://127.0.0.1:3333).

Порт публикуется только на `127.0.0.1`. PostgreSQL снаружи не публикуется. Логин в локальном режиме не требуется. Для остановки используйте `docker compose down` без `-v`. Для обычного обновления снова выполните `docker compose up -d --build`: тома БД, ключа шифрования и резервных копий остаются.

В «Настройках» сохраните ключ OpenRouter и выберите модель в каталоге либо введите точный model ID вручную. Список моделей может быть недоступен; ручной ввод работает отдельно. Ключ не надо помещать в `.env` и присылать кому-либо в сообщении. После сохранения API возвращает только маску. Запуск анализа отправляет текст референса в OpenRouter. Проверка каталога не вызывает генерацию. Реальный платный тест интеграции выполняется только по отдельному разрешению на конкретную модель и расход.

Во время анализа плашка задания показывает фактический этап, прошедшее время и объем уже полученного ответа без выдуманного процента. Ошибка остается видимой и допускает явный повтор; исходный текст при этом сохраняется. Лимит контекста относится к модели **текущего цикла** и показан рядом с ее ID. Созданные при разработке синтетические проекты находятся в архиве, их можно открыть кнопкой «Показать архив».

Для локальных автоматических тестов можно временно указать `AI_ADAPTER=test` в `.env`. Интерфейс показывает «ТЕСТОВЫЙ АДАПТЕР». Этот режим генерирует заранее заданные ответы и не доказывает работу OpenRouter. Удалите эту настройку перед реальной работой и пересоздайте контейнеры командой запуска выше.

## Данные и резервные копии

Compose использует именованные тома `database`, `keys`, `backups`. Перед миграцией существующей схемы сервис `backup` делает дамп PostgreSQL формата `-Fc` в томе `backups`. Копии сохраняются без автоматической очистки; контролируйте доступное место и срок хранения самостоятельно. Master key находится в отдельном томе `keys`. **Для восстановления нужны и дамп БД, и этот ключ.** Если key том утрачен, старые зашифрованные ключи OpenRouter не расшифруются; приложение выдаст явную ошибку.

Пример проверки файлов копий: `docker compose run --rm backup sh -c "ls -lh /data/backups"`. Команда `docker compose run --rm backup sh /scripts/verify-backup.sh` пробно восстанавливает последний дамп во временную БД, сверяет наличие проектов, версий и записей ключей, затем удаляет только эту временную БД. Для восстановления рабочей установки сначала остановите web и worker, сохраните отдельную копию текущих томов, затем восстановите совместимую версию БД через `pg_restore` из нужного дампа и верните соответствующий том `keys`. Не откатывайте образ на старую несовместимую схему. Не используйте `docker compose down -v` при обновлении и восстановлении.

## Разработка и проверки

Стек: Next.js App Router, React, TypeScript, Tailwind CSS, PostgreSQL, Prisma, Zod и pg-boss. API и worker находятся в отдельных модулях. Тестовый адаптер включается только переменной окружения.

Шрифты Oswald Regular и Huninn загружаются из локальных WOFF2-файлов в `public/fonts`, поэтому интерфейс не зависит от Google Fonts при работе. Их лицензии SIL Open Font License находятся рядом с файлами шрифтов.

```text
npm ci
npm run db:generate
npm run typecheck
npm run lint
npm test
npm run build
```

Основной запуск и проверка миграций выполняются через Docker. Описание HTTP-операций — в [docs/API.md](docs/API.md), результаты AC-01–AC-32 — в [docs/AC-REPORT.md](docs/AC-REPORT.md). ТЗ — [TECHNICAL_SPEC.md](TECHNICAL_SPEC.md).


## Метод формирования голоса

Результаты проверок, сохранность данных и границы приемки описаны в [отчете метода 2](docs/METHOD-ACCEPTANCE.md).

Новые проекты и циклы используют метод 2. Укажите у референса роль «Мой голос», «Ориентир» или «Не указано» и запустите анализ. Во вкладке «Приемы» появятся две группы с описаниями звучания и чекбоксами. У карточек различаются переносимая форма и особенности темы; автор и цитаты остаются в анализе.

Отметьте нужные приемы, добавьте пожелания и нажмите «Сформировать правила». Во вкладке «Правила» модель предложит кандидаты в двух колонках. Все новые кандидаты не выбраны. Отмечайте и правьте нужные формулировки, раскрывайте их основания и условия. Для «Не делай так» выберите «Нежелательно» либо «Запрет». Можно добавить собственное правило. В сборку инструкции попадут только отмеченные правила.

Повторная генерация добавляет новые невыбранные предложения и сохраняет рабочий набор. Фильтр позволяет вернуться к прежним предложениям. Когда меняются приемы или пожелания, основание старых кандидатов отмечается как устаревшее; это не запрет сохранения и экспорта. Каждое правило имеет историю правок, а именованная версия сохраняет оба уровня выбора и роли источников.

Существующие циклы остаются на прежней методике. В их рабочей области есть действие «Начать новый цикл по методу»: оно копирует источники и их роли, сохраняя прежний цикл с документами и историей. Платный анализ запускается только отдельной командой пользователя.

Для детерминированной приемки есть `compose.method-test.yaml`: он поднимает отдельный тестовый экземпляр на 3334, использует tmpfs для БД и не подключает рабочие тома или ключи. После сборки образа `ai_voicers-web` запустите `docker compose -p ai_voicers_method_test -f compose.method-test.yaml up -d`, затем `docker compose -p ai_voicers_method_test -f compose.method-test.yaml exec -T web node scripts/method-smoke.mjs`. Скрипт браузерной проверки — `node scripts/method-browser.mjs`. Остановка тестового экземпляра: `docker compose -p ai_voicers_method_test -f compose.method-test.yaml down`.
